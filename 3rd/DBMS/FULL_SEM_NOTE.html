1.1 What is a Database and Why Do We Need It?

The Problem: Imagine a university with 10,000 students, 500 courses, 50 instructors. Without a database, data lives in text files — students.txt, courses.txt, enrollment.txt. If "John Smith" changes his name, you must update three files manually. Miss one → data inconsistency.

Example: File-Based System Tables

students.txtcourses.txtenrollment.txt
CS001, John Smith, CS
CS002, Alice Johnson, EE		 CS101, Programming, Prof. A
CS102, DBMS, Prof. B		 CS001, CS101
CS001, CS102
CS002, CS101
Redundancy Example: John Smith's name appears in students.txt, and if there were library.txt and sports.txt too. Updating only one file creates inconsistency.
📁 File System Problems
  • Redundancy — Same data stored multiple times
  • Inconsistency — Different versions of same data
  • Poor Security — No central control
  • Concurrency Issues — Hard to handle multiple users
  • Retrieval Difficulty — Data scattered everywhere
🗄️ DBMS Solution
  • Data stored once, referenced everywhere
  • One update → consistent everywhere
  • Many users access simultaneously
  • All data organized in one place
  • Fine-grained access control
💡 Analogy

If the database is a filing cabinet, the DBMS is the librarian — organizes everything, finds anything, controls access, never loses data.

1.2 Data Abstraction — Hiding Complexity

Like driving a car without knowing how the engine works. Databases hide internal complexity behind simple interfaces.

🔍 VIEW LEVEL (Top Floor)
What users see — "Show me my grades"
▼
🧠 CONCEPTUAL LEVEL (Middle)
What data exists — "Students take Courses"
▼
💾 PHYSICAL LEVEL (Ground)
How data is stored — "Files on disk, B-tree indexes"
Level 1
💾 Physical

How data is stored on disk. Who cares: DBAs. Example: Records stored on blocks 100–150.

Level 2
🧠 Conceptual

What data exists and relationships. Who cares: Designers. Example: Students have IDs, names, departments.

Level 3
🔍 View

What each user sees. Who cares: End users. Example: Registrar sees grades; HR sees department only.

Data Independence

🔧 Physical Independence

Change storage without affecting users. Example: Add an index to speed up search — users don't notice.

📊 Logical Independence

Change data structure without breaking views. Example: Add an "email" column; adjust views as needed.

2.6 Functional Dependencies

FD: If two rows have same X, they must have same Y. Notation: X → Y

Example FD Table

EmpIDNameDeptSalary
101AliceIT60000
102BobHR45000
103CharlieIT55000

FDs: EmpID → Name, EmpID → Dept, EmpID → Salary. Not Dept → Salary (IT has two different salaries).

Reflexivity

If Y ⊆ X, then X → Y

Augmentation

If X → Y, then XZ → YZ

Transitivity

If X → Y and Y → Z, then X → Z

Candidate key: Minimal set of attributes that determines all others. Found via attribute closure.

B-Trees · Hashing · ACID · 2PL · WAL · ARIES

3.1 Indexing — Finding Data Fast

Like an index at the back of a textbook. Without index: check every book → O(n). With index: go straight to shelf → O(log n).

Example Index Structure

Index Key (emp_id)Data Pointer
101Block 1
201Block 2
301Block 3
📊 Ordered (B-Tree/B+ Tree)

Keys sorted. Good for equality, range, sorting.

#️⃣ Hash Index

Keys mapped to buckets. Good for equality only.

Dense vs Sparse

Dense: One entry per record. Sparse: One entry per block.

Primary vs Secondary

Primary (Clustering): Data physically sorted as index. Secondary (Non-clustering): Data NOT sorted, points to records.

3.2 B-Trees and B+ Trees

Shallow tree → few disk reads. Self-balancing → O(log n). Sorted order → range queries.

4.3 Authorization — What Can You Do?

Object Privileges

SELECT · INSERT · UPDATE · DELETE · REFERENCES · EXECUTE · ALL PRIVILEGES

System Privileges

CREATE USER · CREATE TABLE · DROP ANY TABLE · BACKUP ANY TABLE

Principle of Least Privilege

Give users only the minimum privileges they need. ❌ Clerk ALL PRIVILEGES → ✅ Clerk SELECT only.

4.4 Access Control Models

DAC

Discretionary: Owner decides access. GRANT/REVOKE. Flexible, intuitive.

MAC

Mandatory: Central authority assigns labels. Bell-LaPadula: No Read Up, No Write Down.

RBAC

Role-Based: Permissions → Roles → Users. Simplified administration.

Bell-LaPadula: Secret user can read ≤ Secret, write ≥ Secret. Cannot read Top Secret. Cannot write to Confidential.

4.5 Encryption — Protecting Data

🔐 Symmetric (AES)

Same key for encrypt/decrypt. Fast. Good for bulk data. Problem: key sharing.

🔑 Asymmetric (RSA)

Public key encrypts, private key decrypts. Slower. Used for key exchange & signatures.

DBMS auto-encrypts files on disk. Application sees plaintext. Protects backups & stolen drives.

4.6 Lessons from Real Breaches

🎮 Sony PSN (2011)

77M accounts. SQL injection, weak MD5 passwords. Lesson: parameterized queries, strong hashing.

🏦 Equifax (2017)

148M people. Unpatched Apache Struts. Lesson: patch management.

📊 Cambridge Analytica (2018)

87M profiles. Abuse of authorized API access. Lesson: least privilege, audit third-party access.

🏨 Marriott (2018)

500M guest records. Undetected compromise since 2014. Lesson: M&A security due diligence, MFA.

5.3 Security in Data Warehousing

🎭 Aggregation Problem

Users can infer individual data by combining aggregate queries. Example: Average salary in a department of 1 employee.

🕵️ Inference

Use non-sensitive data to deduce sensitive facts. Prevention: cell suppression, k-anonymity, differential privacy.

🎭 Data Masking

Replace sensitive data with realistic but fake data. Static, Dynamic, On-the-fly.

📋 Auditing

Track who did what, when, where. Essential for compliance and incident response.

Question 3 — 3NF vs BCNF

3NF: No transitive dependency. BCNF: Every determinant must be a candidate key. Example: R(A,B,C) with FDs {AB→C, C→B} satisfies 3NF but violates BCNF.

Question 4 — Shared vs Exclusive Locks

Shared (S): For reading, multiple transactions can hold simultaneously. Exclusive (X): For writing, only one transaction can hold.

Question 5 — Star Schema for Sales

Fact: Sales_Fact(SaleID, DateKey, ProductKey, CustomerKey, StoreKey, Quantity, Amount). Dimensions: Date, Product, Customer, Store.
